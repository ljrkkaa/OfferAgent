# Codex Subscription stateless multi-round context contract

Status: research note (not a product specification)
Checked: 2026-07-19
Scope: multi-round Responses requests with `store: false` and no
`previous_response_id`, including OfferAgent's JSON `AgentStep` loop and the
Codex Subscription standard/lite request dialects

## Executive conclusion

With `store: false` and no `previous_response_id`, each Responses request is
independent. The caller must reconstruct the complete model-visible context on
every request: the effective developer/model instructions, prior user input,
all prior `response.output` items in order, and the next observation or user
input. OpenAI's stateless example appends the complete `response.output`, not
only `output_text`; it explicitly calls out reasoning items. Stateless
reasoning continuity also requires requesting and replaying
`reasoning.encrypted_content` when the model returns it.
[OpenAI conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state#manually-manage-conversation-state),
[Responses `include` reference](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-include)

The public Responses message role enum is exactly `user`, `assistant`,
`system`, or `developer`. It does **not** contain `tool`. Typed tool-output
items are legal, but their `call_id` is the unique identifier generated by a
corresponding model tool call. The documented tool loop first preserves the
model's `function_call` item and then appends a `function_call_output` with that
same `call_id`.
[Responses input-message roles and `phase`](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-input),
[Responses function-call item definitions](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-input),
[OpenAI function-calling loop](https://developers.openai.com/api/docs/guides/function-calling#handling-function-calls)

OfferAgent's current design is a different protocol: the model emits an
application-defined JSON `AgentStep` inside an ordinary assistant response,
and OfferAgent executes the selected tool locally. No native Responses
`function_call` or `custom_tool_call` exists, so there is no authentic native
`call_id`. It would be protocol forgery to manufacture a
`function_call_output` or `custom_tool_call_output` for that operation.

The narrowest legal projection is therefore:

1. preserve the model's JSON `AgentStep` by replaying the exact assistant
   `response.output` items;
2. append the local execution result as a normal `user` `input_text` message,
   in a bounded, escaped, explicitly untrusted data envelope that carries an
   OfferAgent-owned correlation identifier;
3. send the resulting full history on the next stateless request.

`user` is the least misleading public role: local execution output is not a
developer instruction and was not generated by the assistant. Official Codex
also represents some out-of-band observations, including a user shell command
result and a subagent status notification, as delimited `user` context.
However, OpenAI does not publish a normative recipe for an application-defined
JSON-agent loop. The role choice and envelope below are therefore an
evidence-based OfferAgent design conclusion, not a newly discovered OpenAI
wire type.
[Codex user-shell observation](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/context/user_shell_command.rs#L29-L47),
[Codex subagent observation](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/context/subagent_notification.rs#L20-L41)

Codex Subscription standard and lite dialects do not change that conclusion.
They change how the catalog baseline and advertised tools are placed at the
front of a request, not the legal role of an ordinary historical message or
the requirement to replay history. Standard places the resolved baseline in
top-level `instructions`; Lite prepends developer `AdditionalTools` and
baseline items to `input`, leaves top-level `instructions` empty, and requests
all-turn reasoning context. Both then send the same conversation input vector.
[Codex standard/lite request construction](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/client.rs#L810-L908)

## 1. Stateless replay contract

OpenAI describes each text-generation request as independent and stateless.
Its manual Responses example uses this exact sequence:

```text
history = [initial user message]
response = responses.create(input=history, store=false)
history += response.output
history += [next user message]
response = responses.create(input=history, store=false)
```

The example comments say to append **all** output items, including encrypted
reasoning items. The create-response reference separately says that including
`reasoning.encrypted_content` enables reasoning items to be used in stateless
multi-turn conversations such as `store: false` or zero-data-retention use.
[official JavaScript and Python stateless examples](https://developers.openai.com/api/docs/guides/conversation-state#manually-manage-conversation-state),
[encrypted-reasoning purpose](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-include)

For OfferAgent this yields these replay rules:

- Keep the exact ordered input/output item history for the run. Do not reduce a
  prior response to the parsed `AgentStep` object or reconstructed plain text.
- Request `reasoning.encrypted_content` and replay returned reasoning items.
  The caller need not and cannot inspect the encrypted reasoning body.
- Preserve the `phase` field on every assistant message that has one. The
  Responses reference says this is important for `gpt-5.3-codex` and later and
  that dropping it on follow-up requests can degrade performance.
- Re-send the effective model/developer instruction layers on every request.
  No server-side chain is being selected to restore them. Even when
  `previous_response_id` is used, the API explicitly says prior top-level
  `instructions` are not carried forward; a fully manual stateless loop must
  not assume implicit instruction persistence either.
- Append the newly available local result or new user input only after the
  assistant output that caused it. Ordering is part of the history.

[Responses assistant `phase` contract](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-input),
[top-level `instructions` persistence note](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-instructions)

Official Codex follows the same full-history model. Before each sampling
request it clones conversation history, filters it for the model's supported
input modalities, and supplies that vector to the request builder. Retries do
the same after the first attempt. Its request preparation removes item IDs when
the provider does not store items, but it does not discard the historical
items.
[Codex per-sample history replay](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/session/turn.rs#L266-L289),
[Codex retry replay](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/session/turn.rs#L1123-L1167),
[non-stored item-ID preparation](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/client.rs#L911-L925)

## 2. Legal roles and typed output items

The public Responses API separates ordinary messages from typed tool-protocol
items:

| Candidate representation | Public Responses status | Meaning for OfferAgent's JSON loop |
| --- | --- | --- |
| `developer` message | Legal | Trusted application instruction. A local tool result must not be upgraded to this authority. |
| `system` message | Legal | High-authority instruction. Also misleading and too authoritative for local result data. |
| `user` message | Legal | Ordinary external input. Best legal projection for a non-native local observation. |
| `assistant` message | Legal | Presumed by the API to have been generated by the model previously. Correct for replaying the model's `AgentStep`, not for locally generated results. |
| `tool` message | **Not legal** | Not in the Responses input-message role enum. `role: tool` belongs to other API shapes such as Chat Completions and must not be copied into Responses. |
| `function_call_output` | Legal only as a typed item paired with a model call | Requires the `call_id` generated by a preceding native `function_call`; not available in the JSON `AgentStep` design. |
| `custom_tool_call_output` | Legal only as a typed item paired with a model custom-tool call | Requires the `call_id` generated by a preceding native `custom_tool_call`; not available in the JSON `AgentStep` design. |

The first four role meanings and the exact public role enum are specified in
the create-response reference. In particular, the reference says assistant
messages are presumed to have been generated by the model in previous
interactions.
[Responses input message definition](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-input)

For native tools, OpenAI defines tool output as the response to a particular
model tool call and says it should reference that call. The API schema calls a
function call's `call_id` the unique ID generated by the model and gives the
same definition to the output's `call_id`. The official example preserves the
complete `response.output`, locates actual `function_call` items, and copies
each `item.call_id` into its corresponding `function_call_output`.
[function-calling concepts](https://developers.openai.com/api/docs/guides/function-calling#how-it-works),
[function-call handling example](https://developers.openai.com/api/docs/guides/function-calling#handling-function-calls),
[Responses call/output schema](https://developers.openai.com/api/reference/resources/responses/methods/create#responses-create-input)

Official Codex makes the same distinction internally. Its response-input
protocol has an ordinary `Message` plus separate `FunctionCallOutput`,
`McpToolCallOutput`, `CustomToolCallOutput`, and `ToolSearchOutput` variants;
each output variant carries a `call_id`. Its turn loop executes a native model
function call and returns its output in the next sampling request, whereas an
assistant-only response completes the turn.
[Codex response-input variants](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/protocol/src/models.rs#L671-L707),
[Codex native call loop](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/session/turn.rs#L130-L142)

Therefore an OfferAgent correlation value found inside application-defined
assistant JSON is not interchangeable with a Responses `call_id`. Reusing its
string in a typed native output would falsely claim that the backend emitted a
native call and could be rejected, mis-associated, or handled under semantics
that never occurred.

## 3. Honest projection for local `AgentStep` results

For the present architecture, the recommended next-turn suffix is conceptually:

```json
[
  "... exact prior input items ...",
  "... exact prior response.output items, including the AgentStep message ...",
  {
    "type": "message",
    "role": "user",
    "content": [
      {
        "type": "input_text",
        "text": "<offeragent_tool_result>\n{\"agent_step_id\":\"...\",\"tool\":\"...\",\"status\":\"...\",\"result\":{}}\n</offeragent_tool_result>"
      }
    ]
  }
]
```

This is illustrative, not an OpenAI-defined schema. OfferAgent should own and
version the inner envelope. The production encoder should:

- use an OfferAgent name such as `agent_step_id`, not `call_id`, so the value
  cannot be confused with a native Responses tool-call identifier;
- serialize the result as data with escaping and fixed outer delimiters;
- label the body as local tool output and untrusted data, not instructions;
- include the tool name, correlation identifier, completion/error status, and
  a bounded result payload;
- preserve attachment or multimodal result parts only through content types
  that the selected model and public role actually accept;
- apply truncation/redaction policy before the body enters model context.

The model will see this because it is a legal input message included in the
next request. That is not a guarantee that the model will reason correctly
about the value or obey the application protocol; behavioral confidence still
requires end-to-end tests. Delimiting and labeling untrusted tool output also
does not turn it into trusted instructions or eliminate prompt-injection risk.

Why `user` is preferable here:

1. It does not falsely claim model authorship, unlike `assistant`.
2. It does not grant instruction authority, unlike `developer` or `system`.
3. It is legal in the public Responses message enum, unlike `tool`.
4. It does not invent a native tool-call relationship, unlike a typed call
   output without a backend-generated call item.
5. Official Codex uses delimited user-role context for analogous external
   observations such as shell results and subagent notifications.

The fifth point is supporting precedent, not proof of a required universal
mapping. Codex's actual native tools use typed call/output pairs when such a
pair exists.

## 4. Standard and Lite subscription dialects

The official Codex client first obtains the formatted conversation input from
the same `Prompt`. It then applies one of two request prefixes:

```text
standard Responses:
  instructions = resolved catalog baseline
  input        = full conversation/application history
  tools        = normal Responses tools

Responses Lite:
  instructions = ""
  input        = [developer AdditionalTools,
                  developer resolved catalog baseline,
                  full conversation/application history]
  tools        = absent
  reasoning.context = all_turns
```

[official request branch](https://github.com/openai/codex/blob/312caf176a8fd3a5897a3d1fd3ed0a283bd1b5ac/codex-rs/core/src/client.rs#L810-L908)

The consequence for multi-round history is deliberately small:

- Standard must send the effective catalog baseline as top-level
  `instructions` on every stateless request.
- Lite must rebuild its developer prefix on every stateless request. The
  baseline does not become historical assistant/user content merely because
  it is in `input`.
- Application-owned developer messages, prior user messages, exact assistant
  output items, and the next local-result user projection remain in their
  original order after the dialect prefix.
- The local-result role does not change between Standard and Lite.
- `include: ["reasoning.encrypted_content"]` is still used by official Codex;
  Lite's `reasoning.context = all_turns` is an additional dialect setting, not
  a substitute for replaying conversation items.

`AdditionalTools` and the complete subscription-backend Lite contract are not
part of the public Responses OpenAPI documented on developers.openai.com.
Their existence and placement are evidenced by the first-party Codex source,
but a third-party client cannot infer undocumented variants beyond that source
or assume they are stable. This research does not claim that a public API-key
Responses endpoint accepts the private `AdditionalTools` item.

## 5. Recommended OfferAgent request sequence

For each model sampling step, the adapter should construct the request from
durable run history rather than only the most recent prompt:

1. Resolve and freeze the catalog model baseline and standard/lite dialect for
   the run.
2. Build the dialect-specific model prefix for the current request.
3. Append trusted OfferAgent application/developer messages.
4. Append the initial user task and all subsequent input items in order.
5. After every model response, persist and later replay every relevant
   `response.output` item, including assistant `phase` and encrypted reasoning.
6. Parse the assistant text into `AgentStep` for local orchestration without
   replacing the original wire-history item.
7. Execute the selected local tool.
8. Append its result as a delimited `user` `input_text` data envelope with an
   OfferAgent-owned correlation ID.
9. Send the entire reconstructed context with `store: false` and no
   `previous_response_id`.

If OfferAgent later adopts native Responses function/custom tool calls, that
vertical slice should use the native call item and matching typed output with
the model-generated `call_id`. It must not mix that protocol with the JSON
`AgentStep` projection. Hosted tools whose call/output items are emitted by the
Responses service should likewise retain and replay their native items rather
than be converted to the user envelope described here.

## 6. Explicitly unpublished or unproven details

The first-party sources do **not** establish:

- an OpenAI-standard envelope for locally executed tools selected through
  arbitrary assistant JSON;
- permission to synthesize native call IDs for a non-native agent protocol;
- a public OpenAPI definition for Codex Subscription `AdditionalTools` or the
  full Lite backend validator;
- a guarantee that every Codex Subscription model will interpret an
  OfferAgent user-role result envelope correctly;
- a guarantee that context placement alone makes the JSON-agent loop robust
  against prompt injection, truncation, malformed results, or model drift;
- whether all private subscription backend details remain identical across
  future Codex versions.

Those gaps require implementation-level contract tests and real subscription
qualification. They do not weaken the protocol conclusions that `role: tool`
is invalid in public Responses, native output items require authentic model
calls, or a stateless caller must replay complete context.
